# PAWJAI Security Audit Playbook

Use this before shipping changes that touch auth, admin, adopter data, storage, payments/donations, bookings, or Supabase policies.

## First Checks

- Run `npm run verify` and note any failures.
- Run `rg -n "createAdminClient|SUPABASE_SERVICE_ROLE|service_role|isAdminGateOpen|storage\\.from|dangerouslySetInnerHTML" app utils lib`.
- Check `git status --short` before editing. Do not remove user changes.

## App Security

- Service-role client must stay server-only.
- Any service-role mutation needs a preceding authorization check.
- User-owned actions should prefer the user-scoped Supabase server client and RLS.
- Admin pages and admin server actions must enforce admin access, not just hide UI.
- Shared shelter accounts must be scoped through `shelter_users`; do not authorize by email domain alone.
- Privileged admin changes should be visible in `admin_audit_events` without storing raw private document or message content.
- File uploads need type, size, count, and path validation.
- Keep private document URLs signed and short-lived.
- Avoid rendering raw HTML. If `dangerouslySetInnerHTML` is required, prove the input is generated by trusted code.

## Supabase Security

- RLS must be enabled on exposed public-schema tables.
- Views should use `security_invoker = true` or stay unexposed.
- Avoid `security definer` functions in exposed schemas.
- Do not authorize from `raw_user_meta_data` or user-editable JWT claims.
- Storage upserts need the right INSERT, SELECT, and UPDATE policy combination.
- Re-run generated TypeScript types after schema changes.

## Production Readiness

- No hardcoded admin fallback secrets.
- No `NEXT_PUBLIC_*` server secrets.
- Dependency audit reviewed.
- Security headers reviewed.
- Rate limits or abuse controls considered for public forms and uploads.
- Privacy policy and retention behavior match collected adopter documents.
